# 延迟突增

## TTFT

从请求发出到第一个 Token 到达的时间。影响原因：网关排队、上下文构建、首轮检索、模型服务排队和模型预填充。

页面迟迟没有内容，用户一直面对空白。

## 总时延：开始输出快，但任务迟迟不结束

指请求发出到任务完成的时间。影响原因：模型生成速度、工具调用、Planner 决策、失败重试、反思次数和任务步数。流式输出不代表任务完成更快。

## 如何通过 Trace 定位

1. **圈定范围**：按任务、模型、工具和版本比较 P50、P95、P99，区分普遍变慢和少量长尾。
2. **串起链路**：Trace ID 关联整次任务，Span 记录各环节耗时、状态、Token、步数和重试；跨服务传播上下文，敏感内容脱敏。
3. **对照排查**：比较同类正常与慢 Trace，沿瀑布图找决定完成时间的关键路径，再结合日志和资源指标确认原因。

## 对症优化

- **排队**：扩容、限并发、背压。
- **模型**：按难度路由，精简上下文和输出，利用缓存。
- **检索与工具**：连接复用、批量、缓存；独立且副作用可控的调用才并行。
- **编排与重试**：减少重复步骤，设置停止条件和预算；仅重试临时错误，有副作用的调用保证幂等。

## 面试容易踩的坑

- 默认是模型慢，未查链路就换模型。
- 只看平均值，忽略 TTFT、总时延和尾延迟。
- 把最长 Span 当根因，或直接累加父子、并行 Span。
- 不顾依赖和下游容量，盲目并行。
- 只验证速度，忽略成功率、质量、安全和成本。

**验证闭环**：历史轨迹回放 → 灰度对比同口径指标 → 确认质量等指标无不可接受的退化 → 纳入监控和回归集。
